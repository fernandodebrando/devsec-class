Seção 2 — Design Seguro e Modelagem de Ameaças
Teoria + Lab⏱ 1hSTRIDE · Threat Dragon
▼
Corrigir no design custa 10× menos do que corrigir no código. Corrigir no código custa 10× menos do que corrigir em produção.
— A premissa que justifica investir tempo em Threat Modeling antes de escrever a primeira linha

Threat Modeling é uma abordagem estruturada para identificar, quantificar e priorizar ameaças durante a fase de design — antes que elas virem código, e muito antes de virarem incidente.

STRIDE — seis categorias de ameaça

S
Spoofing
Falsificação de identidade
T
Tampering
Adulteração de dados
R
Repudiation
Negação de ações
I
Information Disclosure
Vazamento de informações
D
Denial of Service
Negação de serviço
E
Elevation of Privilege
Escalação de privilégios

DREAD — priorizando as ameaças identificadas

Depois de identificar as ameaças com STRIDE, o DREAD ajuda a priorizar qual delas ataca primeiro na mitigação:

LetraCritérioPergunta-chave
DDamageQual o estrago se a ameaça for explorada?
RReproducibilityQuão fácil é reproduzir o ataque?
EExploitabilityQuão fácil é executar o ataque?
AAffected usersQuantos usuários são afetados?
DDiscoverabilityQuão fácil é descobrir a vulnerabilidade?

Quando aplicar no SDLC?

📋
Fase de Requisitos
Identificar requisitos de segurança junto com os requisitos funcionais.
🎨
Fase de Design
Criar o modelo de ameaças da arquitetura proposta.
⌨️
Fase de Implementação
Validar se os controles definidos foram, de fato, implementados.
🏗️
Mudanças Arquiteturais
Revisar o modelo de ameaças sempre que a arquitetura mudar de forma relevante.

Seção 3 — SAST: Static Application Security Testing
Teoria + Lab⏱ 1h30Semgrep · o "antivírus" do código
▼

SAST analisa código-fonte, bytecode ou binários sem executar a aplicação. Identifica vulnerabilidades por meio de análise de fluxo de dados, análise de fluxo de controle, detecção de padrões inseguros e taint analysis — rastreamento de dados não confiáveis.

👤 Revisão Manual
⏳ Demorada e cara
📉 Limitada pelo tempo disponível
🎓 Depende da expertise do revisor
📏 Difícil de escalar
🔀 Inconsistente entre revisores
🤖 SAST Automatizado
⚡ Rápido e escalável
💯 Analisa 100% do código
✅ Regras consistentes e reproduzíveis
🔌 Integra com IDE e CI/CD
⏱ Feedback imediato ao desenvolvedor

Onde o SAST se encaixa no SDLC?

Ponto de integraçãoDescrição
IDEPlugin para detecção em tempo real durante a codificação
Pre-commitGit hooks que bloqueiam commits com vulnerabilidades críticas
Pull RequestAnálise automática antes do merge
CI/CDGate de qualidade na pipeline de build
Nightly ScansAnálise completa do repositório periodicamente

Antes e depois: SQL Injection corrigido

❌ vulnerável — Python
# entrada do usuário concatenada diretamente na query
def buscar_usuario(nome):
    query = "SELECT * FROM usuarios WHERE nome = '" + nome + "'"
    return db.execute(query)
✅ corrigido — consulta parametrizada
def buscar_usuario(nome):
    query = "SELECT * FROM usuarios WHERE nome = %s"
    return db.execute(query, (nome,))

Seção 4 — SCA: Software Composition Analysis
Teoria + Lab⏱ 1hDependências · SBOM · CVE
▼

Aplicações modernas são compostas de 80–90% de código de terceiros (bibliotecas, frameworks) e apenas 10–20% de código proprietário. É aí que mora boa parte do risco invisível.

⚠ Os riscos dos componentes de terceiros
  • 83% das aplicações contêm vulnerabilidades conhecidas em dependências
  • Dependências transitivas (dependências das dependências) são invisíveis a olho nu
  • Exploits como o Log4Shell afetaram milhões de aplicações globalmente
  • Licenças incompatíveis podem gerar riscos legais, não só técnicos

O que é SCA e como funciona?

  • Analisa manifestos: package.json, requirements.txt, pom.xml, etc.
  • Identifica dependências diretas e transitivas, de forma completa
  • Cruza com bases de CVE (NVD, GitHub Advisory, etc.)
  • Calcula o CVSS Score para priorizar correções
  • Gera SBOM (Software Bill of Materials) para auditoria e compliance

Seção 5 — DAST: Dynamic Application Security Testing
Dia 2 · Teoria + Lab⏱ 1hOWASP ZAP · Nikto
▼

SAST vs. DAST — diferenças fundamentais

🔍 SAST (White Box)
📄 Analisa código-fonte
⏸️ Não executa a aplicação
🔮 Encontra vulnerabilidades potenciais
⚠️ Muitos falsos positivos
⚡ Rápido e barato
🌐 DAST (Black Box)
▶️ Testa a aplicação rodando
🚫 Não precisa do código-fonte
✅ Encontra vulnerabilidades reais
🎯 Menos falsos positivos
🐢 Mais lento e complexo

O que o DAST detecta?

  • Vulnerabilidades de runtime e configuração
  • Headers de segurança faltantes (CSP, HSTS, X-Frame-Options)
  • Autenticação e sessão quebradas
  • Injeções que só aparecem em runtime (SQLi, XSS, Command Injection)
  • Problemas de lógica de negócio e fluxos de autorização

Tipos de DAST Scan

TipoDescrição
Baseline ScanRápido (~5 min), passivo, detecta vulnerabilidades mais óbvias
Full ScanCompleto (~horas), ativo, testa todas as vulnerabilidades conhecidas
API ScanEspecífico para APIs, usa specs OpenAPI/Swagger
Authenticated ScanTesta com credenciais, encontra issues pós-login
Continuous ScanRoda periodicamente em produção para detectar regressão

Seção 6 — Segurança de IaC e Containers
Dia 2 · Teoria + Lab⏱ 1h30Checkov · TFSec · Trivy
▼

IaC (Infrastructure as Code) define infraestrutura através de código declarativo: Terraform (multi-cloud), CloudFormation (AWS), ARM Templates (Azure), Pulumi (programático).

✅ Benefícios do IaC
📜 Versionamento e auditoria
🔁 Reprodutibilidade
🤖 Automação completa
⚠️ Riscos de segurança
📤 Configurações inseguras commitadas no Git
🔓 Permissões excessivas (buckets S3 públicos)
🔑 Secrets hardcoded no código

Principais misconfigurations em Cloud

  • Storage público: buckets S3, Azure Blobs expostos à internet
  • Firewalls abertos: Security Groups com 0.0.0.0/0 em portas críticas
  • IAM permissivo: políticas com wildcard (*) em recursos e ações
  • Encryption desabilitada: dados em repouso sem criptografia
  • Logging desabilitado: impossibilita auditoria e detecção de incidentes

Container Security — principais riscos

  • Imagens vulneráveis: CVEs em base images e dependências do sistema
  • Secrets em imagens: credenciais hardcoded em Dockerfiles
  • Privilege escalation: containers rodando como root
  • Registries inseguros: imagens não assinadas ou de fontes não confiáveis
  • Runtime risks: containers com capabilities excessivas no Kubernetes

Ferramentas de IaC e Container Security
